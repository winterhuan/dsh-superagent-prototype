# 003 执行

[English](003-execution.md) | 中文

本文介绍已接单工单的执行、交付和恢复过程，以 [001 领域模型](001-domain.zh.md)和 [002 授权](002-authorization.zh.md)为基础。

## 工单阶段

每个未结束工单都有一个阶段，由其等待的事项决定。从上到下读取表格，采用首个匹配行。

| 阶段 | 条件 | 面板标签 |
| --- | --- | --- |
| person / delivery | 向执行器会话投递输入失败；2 秒后重试，之后延迟翻倍，最多一分钟。投递成功、新派工或工单结束会清除此状态 | 输入未送达 |
| person / answer | 存在待人工决定的问题 | 等待回答 |
| person / review | 最新报告为 `ready` | 等待评审 |
| person / blocked, failed | 最新报告为 `blocked` 或 `failed`，此后没有人工消息到达工单 | 受阻 · 失败 |
| working / queued | 没有派工，或派工待启动 | 排队中 |
| idle | 最新报告为 `waiting`，或派工已结束 | 等待触发 |
| working | 其余情况 | 执行中 |

`person` 阶段表示工单必须获得人工输入才能继续。新的人工消息将 `blocked` 或 `failed` 工单交回执行器，使其进入下一个匹配阶段，通常是 `working`。

`idle` 工单已结束其轮次，没有未回答问题。已订阅线程中的触发可以使它继续。

## 执行器

每个工单获得名为 `worker-<ticket id>` 的执行器会话，以及以工单短名称命名的目录。目录创建于配置的执行根目录下，默认是 `<stateDir>/work`。

执行器会话以操作者的系统用户身份运行命令，无需审批。其 `dsh-superagent-worker` 预设包含工作所需工具，前台 shell 命令运行 5 秒后转为后台任务。worker 因此可以在下一步骤接收新消息，无需等待长命令完成。

主会话使用 `dsh-superagent-router`，具有相同的 5 秒 shell 和任务等待限制，以及更小的路由工具集。会话保留创建时选择的预设。worker 的 subagent 使用 DeepSeek Harness 的 `standard` 预设。

### 后台工作和 worker 名额

轮次结束时，如果 shell 任务或 subagent 仍在运行，工单保留 worker 名额并保持执行中，不报告为等待，主会话也不会收到等待报告。任务或 subagent 完成后，在同一名额中以结果唤醒执行器。轮次结束且没有后台工作时，执行器才正常报告等待。

每个轮次结束后，后台工作最多有 30 分钟完成。达到限制时，shell 任务被终止，工单报告等待。报告包含执行器最后的话、被终止的任务及仍在运行的 subagent。subagent 可以继续。执行器在下一轮读取被终止任务的结果。

交给人工处理时立即释放名额，并保留报告的效力。这适用于 `ready` 报告或提问后（除非此后又到达输入），也适用于任何 `blocked` 或 `failed` 报告后。

交接时，subagent 停止。用于评审的服务器等 shell 任务可以继续到派工结束，不占名额，也不受 30 分钟限制，包括后续轮次之后。它们完成时不唤醒执行器；执行器在下一轮读取结果。

人也可以直接在执行器会话中写消息来启动轮次，其后台工作遵循相同规则。

派工结束时，其 shell 任务被终止，不唤醒会话。驻留后代中的工作被中断，它们完成时唤醒的轮次被丢弃。后代会话仍可恢复，worker 仍可启动新的 subagent。关闭完成后，替代派工及等待输入才开始。

在 DeepSeek Harness 进程内停止或重启插件使用相同的关闭路径。尚未进入会话历史的输入保留。关闭时最多等待每个 worker 的后台工作 10 秒；进程重启则直接结束这些工作。忙碌时被中断的派工重启后收到恢复说明。

worker 的 subagent（包括嵌套 subagent）使用 DeepSeek Harness 的 `standard` 预设及 worker 权限，只保留 worker 获准使用的工作工具，并在工单结束时失去这些工具。在 `standard` 下，shell 命令运行 60 秒后转为后台。subagent 结束时，其任务被终止。

### 准备工单目录

首次派工前，如果工单目录不存在，准备命令在执行根目录中通过 `sh` 运行一次，最多运行十分钟。没有准备命令时，worker 从空目录开始。

命令失败会使工单失败，并记录输出。重试或工单线程中的人工消息会再次尝试准备。典型命令使用 `git worktree` 创建检出目录。PR（Pull Request）分支路径的最后一段与工单短名称一致时，该 PR 属于此工单。

### 并发

工单从启动开始（包括准备阶段），或从唤醒空闲执行器的输入投递开始，占用一个 worker 名额。活跃轮次期间也持续占用。

配置的并发限制作用于这些名额，并为人工消息或状态请求额外保留一个名额。普通名额已满时，这类唤醒可以使用额外名额；有空闲名额时，也优先于新启动。因此，新工作不会阻止人继续已有工单。

CI 结果等其他输入等待普通名额。启动在名额空闲前保持 `working / queued`。启动并发运行，因此缓慢的准备命令只延迟其自身工单。

### 执行变量

准备命令和执行器指令接收相同的执行变量。命令读取环境变量；执行器从提示词读取值及说明。变量均不含凭据。

| 变量 | 注册者 | 值 |
| --- | --- | --- |
| `DSH_SUPERAGENT_DIR`, `DSH_SUPERAGENT_NAME`, `DSH_SUPERAGENT_TICKET` | 执行器 | 工单目录、短名称和 id |
| `DSH_SUPERAGENT_BLOCKED_COMMANDS` | 执行器 | 执行器不得运行的命令 |
| `DSH_SUPERAGENT_GITHUB_REPOSITORY` | GitHub | 来源监听的仓库，格式为 `owner/name` |
| `DSH_SUPERAGENT_GITHUB_ACCOUNT`, `DSH_SUPERAGENT_GITHUB_COMMIT_EMAIL` | GitHub | agent（智能体）账号及其提交邮箱 |
| `DSH_SUPERAGENT_GITHUB_NUMBER`, `DSH_SUPERAGENT_GITHUB_PR_HEAD` | GitHub | 发起工单的 Issue 或 PR；若为 PR，还包含其 head ref |
| `DSH_SUPERAGENT_FEISHU_BOT`, `DSH_SUPERAGENT_FEISHU_CHAT` | 飞书 | 机器人及发起工单的群 |

工单专属值来自其目录及起始触发。其他值来自当前部署设置。只有面板可以修改执行环境设置；发给主会话的文本不能改变配置的 shell 命令。

worker 通过 agent 账号的 `gh` 访问 GitHub，通过机器人的 `lark-cli` 访问飞书。按名称调用被禁止命令时会失败。

这些包装层和目录建立默认行为，不构成安全边界。worker 仍可通过绝对路径执行程序。

## 合并

自动合并由**交付要求**提示词约束。宿主没有专门的合并决策逻辑。

默认情况下，执行器从不以 agent 账号启用自动合并：GitHub 将合并归于启用它的人。交付要求必须指定另一账号的 CLI（命令行界面）用于合并。没有该 CLI 时，由人合并 PR。

默认指令只允许对为该工单创建的 PR 启用自动合并，且要求 PR 已就绪、必要批准覆盖 head commit、增加和删除的总行数少于 200 行。推送另一版本前，执行器撤回自动合并。

批准等无正文评审也作为触发到达，可以唤醒等待评审的执行器。这些指令约束 agent，不约束 GitHub 的合并规则。要强制要求批准，应在分支保护中设置要求并撤销陈旧批准。省略合并 CLI 或删除自动合并段落，即可要求手动合并。

## 工单如何结束

- **没有 PR 的就绪结果：** `ready` 报告将工单结束为已完成。
- **无需处理：** 执行器发现没有需要人操作的工作，例如无法复现的请求或已被其他工作取代的请求，报告 `dropped`。工单结束且不发消息，除非匹配规则要求发消息；后续人工消息可以通过其线程恢复工单。
### PR

执行器报告工单起始 PR 后，工单关注该 PR。执行器报告或 GitHub 来源发现从工单分支创建的 PR 后，工单也关注这些 PR。重新打开的 PR 会再次被关注。

工单创建的 PR 均不再打开时，工单完成。如果它没有创建 PR，则其关注的所有 PR 都必须关闭。工单按最后一次相关关闭的结果结束，并保留订阅，允许后续人工评论恢复。

恢复、重试或恢复故障后的工作尚未完成时，PR 关闭不结束工单。执行器已确认或回答其拥有的后续消息，但此后尚未作出非进展报告，或尚未在读取该消息后结束轮次时，关闭也需等待。后续 `ready` 报告在满足相同 PR 完成规则后结束工单。

聊天渠道收到一次关于 PR 结果的最终通知。GitHub 已在 PR 上显示该结果。移除工单对 PR 的订阅，也会停止关注该 PR。

因此，「等待评审」表示带有 PR 的 `ready` 报告。

### 后续消息和上下文线程

执行器判断自身工单线程中的人工后续消息，在范围内处理，超出范围或属于其他工单时退回。不再有执行器拥有消息时，它成为主会话候选项。除此之外，主会话只能按人的请求停止工作。

输入进入会话步骤，且之后会话作出报告或结束轮次，才算已读。工单结束时，未确认、回答或退回的未读消息返回评估，详见 [002 授权](002-authorization.zh.md)。已读但未采取行动的消息，例如致谢，不返回评估。

仅为上下文关注的线程仍投递消息，但不让工单拥有人工后续消息，也不恢复已结束工单。这些消息可以独立研判。

来源在有进行中工单订阅时轮询线程，并持续到最后一次触发与订阅工单结束两者中较晚时间的两周后。之后，消息仅通过普通接收路径到达：GitHub 通知或飞书实时事件。

## 失败和恢复

### 执行器受阻或失败

执行器会话报告 `blocked` 或 `failed`，或启动失败或发生错误（记录为 `failed`）时，工单不接收自动输入。

模型提供商或网络的暂时故障、HTTP 408、429、5xx，或连接被拒绝、重置、超时，会先按逐渐增加的退避时间重试三次：启动重新执行，轮次失败的 worker 被要求继续；失败的准备命令不重试。

进入失败状态后，CI 和机器人消息仍记录在工单上，但不投递，也不唤醒会话。

工具保持可用，因此人可以直接在会话中继续。

失败的启动不会自行再次尝试。

人工消息、后续既非 `blocked` 也非 `failed` 的报告，或重试会解除暂停接收。

这一状态由存储的报告和输入推导，因此重启后仍保留。
### 重试

未结束工单处于 `person / delivery`、`person / blocked` 或 `person / failed` 时可重试：新派工重新启动 worker 并接收等待输入，解决这些情况。

人工消息到达受阻或失败工单后，执行器已拥有该消息，因此工单显示为执行中；失败启动重新开始时显示为排队中。此时不再提供重试，除非该消息投递失败。

重试结束当前派工，并在同一执行器会话、目录、分支和 PR 中启动新派工。

执行器模型只在创建会话时应用；已有会话保留其模型。
### 重启

运行中的派工以「宿主已重启」结束，新派工从最早工单开始启动，并收到恢复说明，要求执行器在重复任何外部操作前检查目录、Git 历史和 GitHub。

等待、就绪、受阻或失败的派工保持原样，除非报告后又收到输入，此时也重新启动。

会话、目录、订阅、待处理消息和下述存储工作在重启后保留。各执行器会话将哪些消息写入历史的记录也保留：步骤认领消息后，在模型调用前写入历史。被重启中断的轮次已写入历史的消息，在后续报告或轮次结束后算已读；步骤已认领，但在写入历史前被取消或错误中断的消息算未读。

重试或重启时，新派工再次收到前任派工已获投递、但执行器会话未接收的消息，取消或中断步骤可能丢失这些消息。若会话中仍有一份副本（重启保留或崩溃后持久化保留），则在新派工的首条消息前移除，确保重新投递是唯一副本。
### 存储工作

dsh-superagent 决定之后的操作，例如向主会话转发候选项、后续消息或报告，启动派工或投递输入，都先存储再执行。

转发或投递失败，例如目标会话无法访问时，2 秒后重试，之后延迟翻倍，最多一分钟。启动失败会使工单失败，除非属于上述暂时故障。

每类工作只有在某项连续失败三次后，才在概览的系统问题中报告错误；输入投递失败则显示在对应工单上。

转发给主会话的消息保持顺序，通知也保持顺序；失败项阻挡后续同类项。
### 来源失败

GitHub 来源分别读取各 Issue、PR 和线程：读取失败的错误保留在线程上，下次轮询再试，并计入来源错误。默认连续三次轮询失败后报告来源错误；任何成功轮询都会重置计数。

agent 失去私有仓库访问权限时，GitHub 也返回 404，因此 404 会重试。

通知中的 Issue 或 PR 持续读取失败时，在首次失败一天后丢弃；GitHub 明确报告已删除时立即丢弃。它不再使轮询失败，线程保留错误，来源状态列出该项。

读取位置保持原样，因此后续通知或线程轮询可以读到此前失败遗漏的内容。

飞书事件消费方报告每次失败，订阅话题轮询将各次失败保留在对应线程上。

GitHub 列表或飞书页中的格式错误项被跳过，来源状态统计其数量。
### 渠道失败

出站消息先存储，再作为存储工作发送；重试退避从 5 秒开始翻倍，最多 300 秒。

工单发往同一对话的消息按入队顺序发送，因此确认先于后续回答或结果。只要同一工单发往同一对话的较早消息尚未发出，后续消息就等待，直到较早消息连续失败三次并显示为问题。

其他工单的消息及不属于任何工单的消息不受它阻挡。

已有失败尝试的消息持续显示为系统问题，直到发出或撤回。

只有来源不再监听该对话，或来源明确答复该对话永远无法接收消息时，消息才丢弃；来源关闭时，消息等待。

GitHub 中已删除的 Issue 或被锁定的对话，以及飞书中已撤回或无法再找到的消息，会得到这样的答复。

回复的评审评论已不存在时，改为发到 PR 对话中。

丢弃的消息保留记录，包括丢弃时间、原因及所属工单，因此不会再次入队；丢弃的确认显示为已丢弃，而非已发送。
### 暂停处理

停止派发、新评估、评估超时、输入投递和回复；已经开始的启动等待处理恢复。

来源继续记录触发，运行中的执行器轮次不被中断。

发给已结束工单的人工消息等待：暂停后的首次处理在授权仍符合当时策略时恢复工单。

进行中的评估在暂停期间不会超时；截止时间按暂停时长顺延。
### 无效配置

来源类型拒绝存储的配置时，禁用该来源实例。
