# 002 授权

[English](002-authorization.md) | 中文

授权决定谁可以启动工作，以及工作可以包含什么。本文以 [001 领域模型](001-domain.zh.md)为基础。

宿主强制执行允许名单、规则和授权。消息、评论及引用的文档都是决策输入，不能改变这些权限。

## 触发的两条路径

### 评估：决定是否启动工作

来源记录消息是否直接向 agent（智能体）发出：`mention` 表示提及机器人或 agent 账号，`direct` 表示私信。准入检查发送者和来源策略：

- 允许名单中的人直接向 agent 发出消息，构成明确请求。
- 人在已有工单的线程中发出后续消息，遵循下述规则。
- 其他人工消息使用其接收范围对应的准入表。
- 来源机器人名单中的机器人可以产生推断候选项，不能提出明确请求。其他机器人不获准进入。

### 订阅：继续已有工作

已订阅线程中的每条消息都作为上下文送达订阅它的工单，包括机器人和 CI 消息。这种投递绕过准入，不授予新权限。每个工单仍受其授权限制。

工单自身线程中的人工消息由该工单的执行器判断。主会话将消息附加到工单时也适用这一规则。执行器拥有消息期间，消息不经过评估，不产生决定。各执行器要么在工单范围内处理请求，要么退回消息，由其他路径路由。

工单仍在进行中时，即使人移除了订阅，消息归属仍然有效。已结束但未被人工停止、且有消息等待其恢复的工单也保有归属。

主会话收到后续消息通知。执行器拥有消息期间，主会话只能按人的请求停止工作；接单、附加、忽略和重新入队都会被拒绝。停止仍需经过准入，强度由下述后续消息规则决定。

### 退回和释放后续消息

消息请求的工作超出工单范围或属于另一工单时，执行器将它退回一次。工单保留订阅。如果附加线程无关，执行器退回其在该线程中拥有的消息。

只有不再有工单拥有消息时，消息才进入新的评估。其候选项包含执行器给出的原因。准入将它作为该线程上的普通消息判断，主会话可以接单、附加到别处或忽略。退回工单并不拥有的消息，例如机器人消息或已被人送往评估的消息，不会将任何内容入队。

工单结束时，释放执行器未读或未接手的后续消息。这包括从未送达执行器的消息，以及最后一次报告或轮次结束后送达的消息，前提是执行器未确认、回答或退回它们。不再有其他工单拥有时，每条释放的消息进入评估。停止只结束被停止工单的工作。

已停止工单不会将停止消息再次送入评估，除非另一个工单将它退回。停止它的主会话可以将消息的其余部分接为新工作。

人可以在面板中将有归属的后续消息送往评估。主会话随后将它重新附加到进行中工单时，执行器会再次收到。消息没有有效判断时，面板也提供重新评估。

### 仅用于上下文的订阅

执行器可以关注相关线程，例如其他 Issue 或 PR（Pull Request），以获取上下文。消息送达工单，但不授予权限或后续消息强度。除非主会话附加该线程中的消息，否则其中的人工消息不会恢复已结束工单。主会话关于其他工作的说明也只属于上下文。

未到达任何工单的人工消息走评估路径，包括工单均被人工停止的线程。机器人消息也走评估路径，这与它们是否送达订阅工单相互独立。

## 强度

| 强度 | 情况 |
| --- | --- |
| explicit | 名单中的人直接向 agent 发出消息，或在已有工单的线程中发出后续消息；准入表单元格设为明确请求 |
| inferred | 名单外的人在已有工单的线程中发出后续消息，且其准入单元格并非明确；准入表单元格设为推断候选项；来源机器人名单中的机器人直接向 agent 发出消息，或在来源接收全部消息的范围中发出消息 |
| 不准入 | 其他机器人的消息、准入表忽略的所有内容，以及接单模式为 `off` 时的所有推断情况 |

对名单外的人，即使线程已有工单，明确准入单元格仍优先适用，且在所有接单模式下有效。否则，其后续消息为推断强度，在 `off` 模式下不获准进入。仅为上下文而关注的线程使用准入表，不使用后续消息强度。

## 准入

各来源的策略都有准入表，行表示接收范围：

- **飞书：** 每个配置的群、机器人接收提及消息的其他群，以及私信。只有飞书卡片的**其他群**设为**仅 @** 时，才接收其他群的消息。
- **GitHub：** 新 Issue、新 PR、评论及默认分支 CI。

每行最多三个单元格。每个单元格决定消息成为明确请求、推断候选项，还是不进入：

| 单元格 | 选项 | 默认值 |
| --- | --- | --- |
| 在名单中，未直接向 agent 发出 | inferred、ignore | inferred |
| 不在名单中，直接向 agent 发出 | explicit、inferred、ignore | ignore |
| 不在名单中，未直接向 agent 发出 | inferred、ignore | ignore |

只有来源接收全部消息的范围才提供未直接向 agent 发出消息的单元格，例如设为**全部消息**的飞书群，或开启全部接收开关的 GitHub 范围。CI 结果没有发送者，因此该行只提供最后一个单元格。机器人消息使用机器人名单，不使用这些单元格。

将「名单外、直接向 agent 发出」单元格设为明确后，该范围中的任何人都能通过提及 agent 请求工作。这适用于专门的支持群。推断候选项仍取决于接单模式。后续消息通常绕过该表，但明确单元格仍授予明确强度。

准入表属于策略版本。降低单元格强度不会立即停止按该单元格接单的进行中工单。恢复前重新验证时，可能撤销它们的授权。

### 机器人和自动评审者

宿主将 GitHub Apps、登录名以 `[bot]` 结尾的账号和飞书机器人识别为机器人。来源可以列出 `dependabot[bot]` 等机器人，允许其消息成为推断候选项。它们必须直接向 agent 发出消息，或在接收全部消息的范围中发帖。它们不能提出明确请求，也不能停止工单。

使用普通账号的自动评审者在宿主看来是人。其评论送达订阅工单并产生后续消息通知。团队提示词必须将这些账号标明为自动评审者。

## 候选项路由

主会话使用 `orchestrator_route` 路由明确候选项。一次调用可以包含多个接单、附加、停止或忽略决定。各项独立处理：某项被拒绝或缺少字段，不会阻止其他项执行。

推断候选项通常需要完整研判。只有一种快捷路径：如果卡片明显不涉及任何启用规则，例如普通聊天或无关讨论，主会话可以直接忽略。决定记录 `ignoredFromCard`，以区别于规则研判。主会话从策略提示词部分读取启用规则。

接单推断候选项必须经过研判。准入未认定为明确的触发，直接接单会被拒绝。

## 接单模式和规则

接单模式属于策略：

| 模式 | 效果 |
| --- | --- |
| `off` | 所有推断内容都不成为候选项，例如未直接向 agent 发出的消息、机器人消息或名单外的人的后续消息 |
| `observe`（默认） | 对推断候选项进行研判；肯定的研判记录为标记「本会接单」的忽略决定，不实际接单 |
| `auto` | 推断候选项的研判结果为肯定时接单 |

明确请求在所有模式下有效。先使用 `observe`，审阅记录的决定后再切换到 `auto`。每次研判必须逐一判断所有启用规则，每条恰好一次，无论是否匹配。主动接单至少需要一条匹配规则。

每条规则描述一种主动工作。工单授权记录匹配规则，执行器收到这些规则的名称和指令。

对该工单，规则的流程和通信要求优先于默认值。静默规则可以抑制确认消息；评审规则可以指定合并前必须具备的评审者及批准。适用于所有工单的要求应写在团队提示词部分。

## 策略版本

规则、接单模式及各来源策略共同构成策略版本。每份授权都记录接单时所依据的版本。

版本变更会使正在运行的评估作废，并将其触发重新入队。它还向每个受影响的进行中工单发送策略变更输入，说明以下情况：

- 匹配规则已变更，包含新文本，或不再适用；
- 请求者可能已不能发起工作；或
- 不再接受主动工作，例如从 `auto` 切换到其他模式。

未受影响的工单不收到通知。变更不会立即撤销进行中工单的授权。

来源配置与策略分开。它控制进入系统的内容：读取哪些群，以及某范围接收全部消息还是仅接收提及。授权记录来源及接收范围。恢复要求来源仍监听该线程，但不要求它仍接收其中的全部消息。

来源关闭时，回复等待。来源不再监听目的地时，回复被丢弃。

限制执行器如何处理自身结果的条件，例如何时可以合并，不决定谁能授权工作。它属于 agent 指令，不属于策略。

## 恢复和停止

已结束工单保留授权。其自身线程中的人工消息可以恢复同一项工作，不产生新的评估或决定，与发送者是谁无关。机器人和 CI 不唤醒已结束工单。执行器判断请求是否符合范围，不符合时结束这一轮。

只有三种操作改变授权：接单创建授权，人工停止收回授权，重新验证失败撤销授权。被人工停止的工单保持结束，不再接收任何内容。在该处请求工作需要重新接单。

### 恢复前重新验证

来源必须仍监听原始线程。其余检查取决于授权的依据：

- 明确后续消息的授权通过验证。
- 推断授权需要 `auto` 模式，且匹配规则仍启用。
- 准入表单元格授予的授权，在当前表及发送者名单身份下必须仍获得至少原有强度。因此，移除名单中的发送者可能撤销通过名单内发送者单元格接单的授权。
- 机器人授权要求该机器人仍在来源机器人名单中。推断表单元格和机器人授权还需要 `auto` 模式及启用的匹配规则。
- 其他授权要求发送者仍在来源允许名单中。

重新验证失败时，工单保持结束，不接收任何等待消息。每条消息均视为未到达任何工单；没有其他工单拥有时，消息进入评估。主会话不会被告知消息到达了 worker。处理暂停后也适用这一规则。附加到该工单会被拒绝，继续工作需重新接单。

- **人在线程中说「停止」是普通触发，** 由评估决定停止。执行器不能声明人要求其停止。
- **面板中的停止是命令。** 它直接作用于工单，并记录为手动停止。
- **等待条件属于来源。** 「N 小时未指派负责人」等条件应由来源自行等待并再次检查；评估从不等待。

## 评估未完成时

候选项到达主会话时开始计时。等待投递的时间不计入，未投递的候选项不会超时。

评估超时后将触发重新入队再试。连续重试两次后，第三次超时记录为 `unavailable`。研判失败也记录为 `unavailable`；后续触发可以启动新评估。策略变更或按陈旧策略作出的决定记录为 `unavailable`，并立即按当前版本重新将整批触发入队。

`evals` 健康项报告最近一小时内尚未解决的 unavailable 决定。`scripts/dsh-superagent status` 包含该错误。

只有 unavailable 决定产生不足 24 小时、仍为线程最新决定、未被忽略处理，且线程既未排队也未评估中时，面板才要求人工关注。人可以重新评估触发或忽略该问题。
